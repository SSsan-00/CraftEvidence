# 挙動維持のパフォーマンス改善（2026-09-08）

## 維持する挙動

今回の変更は `ExcelSheetSnapshotService` の読み取りに限定した。
画面、Case/Sideの選択・遷移、画像の開始位置と寸法、行挿入・削除、Undo/Redo、
配置直前の接続・保護・fingerprint確認、自動保存しない動作は変更していない。
参照Excelは変更せず、試験用に生成した一時ブックで検証した。

## 確認したボトルネックと変更

- 罫線の終端確認は、書式だけ残った末尾を含む場合、1セルごとに
  Cells → Borders → Item → LineStyleを取得していた。
  Bordersのインデックス指定で中間Collectionの取得・解放を省略した。
  複数セルの既存Range取得もA1アドレスによる直接取得に変更した。
- 列幅は同じ幅が続く場合も1列ずつ取得していた。
  EntireColumnのColumnWidthとHiddenで均一かつ非表示列がないことを確認できたときに限り、
  先頭セルのWidth（ポイント）を各列へ展開する。
  幅の混在・非表示・一括取得失敗時は従来の個別取得を使う。
  取得値を次回操作へ持ち越すキャッシュは追加していない。

比較試験で、範囲の罫線情報が途中の欠落を見落とすケースと、1行のRangeのColumnWidthが
混在した列幅の先頭値だけを返すケースを検出した。
罫線を小区間ごとに一括スキップする案は取り下げ、最初の欠落で停止する個別走査を維持した。
列幅の均一性は1行のRangeではなくEntireColumnで判断する。

## 実測

Windows / .NET 9 / 実Excel。一時シートのQ3:Q1202に右罫線を設定し、1500行までの
終端確認を計測。列幅はC:AFの30列。各処理を1回ウォームアップ後、3回計測した中央値。

| 対象処理 | 修正前 | 修正後 | 短縮率 |
|---|---:|---:|---:|
| 1,200行の罫線終端確認 | 4,521.67 ms | 3,447.24 ms | 約24% |
| 均一幅・非表示なしの30列取得 | 51.09 ms | 6.46 ms | 約87% |

幅混在時は52.79 → 60.30 ms、幅混在＋非表示時は50.16 → 55.10 msだった。
これらは一括取得条件の確認が増えるため、高速化対象ではない。
数値は読み取り部分の測定であり、アプリ全体や画像配置全体の短縮率ではない。
長い罫線の個別確認は引き続き行数に比例する。

## 回帰確認と再現

- 罫線の通常終端、途中の欠落後に罫線が再開する場合、最終Caseより手前で途切れる場合。
- 列幅の均一・混在、混在＋非表示、均一＋非表示、全列非表示について、従来のセルごとの
  Width取得と辞書の全項目を比較（非表示の幅0を除外する挙動も維持）。
- 既存の実Excelシナリオで接続、配置、行操作、Undo/Redo、保護・イベント状態などを確認。
- 実Excel試験は専用プロセスを使い、試験間のExcel干渉を避けるため直列実行する。

```powershell
dotnet test tests/EvidenceCrafter.Tests/EvidenceCrafter.Tests.csproj -c Release --filter 'TestCategory=ExcelIntegration' --logger 'trx;LogFileName=performance-after.trx' --results-directory artifacts/test-results
.\bootstrap.ps1 -Publish
```

各処理の計測値はTRXの標準出力に残る。速度の閾値によるテスト失敗は設けず、
取得結果の一致を必須にした。初回の修正前測定は既存操作テストと同じシナリオに追加したため、
測定完了後に55秒上限へ到達した。最終版では計測試験を独立させ、各試験の上限を維持している。
